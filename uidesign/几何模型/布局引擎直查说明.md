# 布局引擎直查 —— 不用像素扫描

## 核心结论

**对自己写的 UI，根本不需要扫描。** 直接问布局引擎（浏览器的 DOM / GTK 的 widget tree / Android 的 View 层级），
拿到的是精确值，不是估算值。

像素扫描（icon_detect / OCR）只在**你只有一张图、没有源码**时才必要（比如分析竞品截图）。

## 实测对比（同一个 390×780 登录页）

| | DOM 直查 | icon_detect 扫描 |
|---|---|---|
| Email 输入框 | **294×48 @(48,315)** | 301×52 @(43,313) |
| Password 输入框 | **294×48 @(48,377)** | 302×52 @(45,375) |
| Log in 按钮 | **294×48 @(48,447)** | 300×51 @(44,446) |
| 偏差 | **0** | 每个维度 +3~8 dp |
| 背景色 | `#EDEDED` / `#07C160` | ❌ 拿不到 |
| 字号 | 16px / 17px | ❌ 拿不到 |
| 圆角 | 4px | ❌ 拿不到 |
| 耗时 | 4.0 秒（含浏览器冷启动 3.5s） | 1.0 秒 |
| 需要模型 | ❌ 不需要 | 80MB onnx |

**DOM 直查处处等于 CSS 里写的数字**（CSS 写的就是 `width:294px; height:48px`）。
扫描则是"猜"，框比真实元素大约 5dp——这是 YOLO 回归头的固有偏差，消不掉。

## 用法

```bash
# 需要 websocket-client
pip3 install websocket-client

python3 dom_query.py <html文件> [宽] [高] [像素密度]
python3 dom_query.py dom_demo.html 390 780 1
```

**像素密度参数**：Chrome viewport 已经是 CSS 像素 = dp，所以传 **1**。
只有当你用 `--force-device-scale-factor=3` 截 3x 图时才传 3。

## 输出

- 控制台：所有可见元素的位置尺寸表，`◆` 标记可交互元素
- `dom_result.json`：可交互元素完整属性（含 bg / color / fontSize / borderRadius）

## 原理

Chrome DevTools Protocol (CDP) → `Runtime.evaluate` → 执行 JS：
```js
document.querySelectorAll('*')  →  getBoundingClientRect()
                                →  getComputedStyle()
```

浏览器自己算完的结果，跟你 CSS 写的完全一致，不存在误差。

## 踩到的坑

**① WebSocket 握手 403**
Chrome 153 校验 Origin 头。两个办法都要做：
- 启动加 `--remote-allow-origins=*`
- 连接时用 `websocket.create_connection(url, suppress_origin=True)`

只加 flag 不够，实测仍 403；`suppress_origin=True` 才是关键。

**② `bc` 命令不存在**
测耗时别用 `bc` 算差值，用 Python 的 `time.time()`。

**③ Chrome 启动慢占了大头**
4 秒里约 3.5 秒是浏览器冷启动。查询本身是毫秒级——
要频繁测就让浏览器常驻，复用同一个 CDP 连接。

## 什么时候还是得扫描

| 场景 | 方法 |
|---|---|
| 自己写的 HTML/Blueprint/Compose | **DOM / widget tree 直查** |
| 第三方 App 截图（只有图） | icon_detect + OCR |
| 验证"渲染出来跟设计稿一不一致" | 两者都做，互相对照 |

建议**两个都跑**：直查给真值，扫描给"视觉上实际看到的样子"，
两者对不上说明有渲染层的问题（比如字体回退、DPR 缩放）。
