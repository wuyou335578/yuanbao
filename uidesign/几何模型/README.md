# 几何模型（UI 图标符号解析工具链）

纯 CPU、无需显卡。**核心能力：识别图标符号 → 说出它长什么样 → 画出一模一样的 SVG。**

---

## 它能做什么

对一张 UI 截图，逐个元素输出四件事：

| 输出 | 说明 | 精度 |
|---|---|---|
| **名字** | 模板匹配（内置 25 个 + 自定义库） | 同款图标精确；异款诚实报"未在图标库中" |
| **长什么样** | 闭合区域数、圆度、外接尺寸、线宽、主色 RGB | 数学级 |
| **精确复现** | SVG 矢量文件 | **IoU 0.958 ~ 0.999** |
| **文字** | OCR | 与 OCR 引擎一致 |

**"画出一模一样"是矢量 SVG，不是位图近似** —— 可无限缩放、可改颜色、可直接放到代码里用。

---

## 快速开始

```bash
# 一键：检出 → 命名 → 说外观 → 生成 SVG
python3 ui_icon_report.py <截图> --dp 3 --out 输出目录

# 单独用：只做几何测量
python3 geo_analyze.py <图> --json out.json

# 单独用：只做矢量还原
python3 icon2svg.py <图> x1,y1,x2,y2 --out 目录
```

`--dp 3` 是截图的像素密度（3x 图填 3，1x 图填 1）。填错只影响 dp 换算，不影响 SVG。

## 文件说明

| 文件 | 作用 |
|---|---|
| `ui_icon_report.py` | **主入口**，串起全流程，输出 report.txt / report.json / cmp_all.png |
| `icon2svg.py` | 单个图标 → SVG 矢量 + 渲染回位图 + IoU 复现精度 |
| `icon_match.py` | 图标命名。内置 25 个模板，支持自定义库 |
| `geo_analyze.py` | 通用几何测量：圆/多边形/直线/角度/颜色 |
| `parse.py` | icon_detect 封装（元素检出） |
| `ui_scan.py` | 元素检出 + OCR + 语义描述三件套 |
| `dom_query.py` | 布局引擎直查（自己写的 UI 用这个，零误差） |

## 模型权重

| 文件 | 用途 |
|---|---|
| `icon_detect.onnx` (77M) | 可交互元素检出，OmniParser 架构 |

## 实测成绩

真实聊天输入栏截图（1440×247，7 个元素）：

```
#0  IoU=0.999   绿色竖条 RGB(31,176,109)  ← 文本光标
#1  IoU=0.961
#2  IoU=0.958
#3  IoU=0.972
#4  IoU=0.964   ⊕ 圆环加号：外环外径 88.5px、线宽 5px、十字 44×44px
#6  IoU=0.980
```

几何测量精度（真值已知的自绘图）：

| 项目 | 真值 | 实测 | 误差 |
|---|---|---|---|
| 圆心 | (105,105) | (104,104) | 1~2 px |
| 边长 | 150 | 152 | 1~2 px |
| 等边三角形角度 | 60° | 60.1° | 0.1° |
| 填充色 | RGB(240,180,40) | RGB(240,180,40) | **零误差** |

## 已知边界（重要）

**1. 命名能力弱于复现能力。**
实测 7 个图标只认对 1 个。原因是不同 App 的图标风格（线宽、圆角、比例）差异大，几何匹配对不上。

**解法：教它一次，永久记住。**
```python
from icon_match import save_template
save_template("麦克风", 图)    # 存进 iconlib/
```
之后同款图标精确匹配。App 图标就那几十个，攒一遍就齐了。

**2. 低于 0.42 分一律报"未在图标库中"，不瞎猜。**
宁可说不确定，也不套一个错名字。

**3. AI 语义模型在这类图标上更差。**
实测 icon_caption 在同样 4 个图标上只说对 1 个（把麦克风说成"用户头像"、把声音说成"刷新"）。所以本工具链**不依赖 AI 做命名**。

**4. 复杂曲线会拟合失真。**
齿轮实测被识别成"八边形"。轮廓简化容差 `EPS` 可调小改善，但顶点数会上升。

## 更新记录（第二轮）

### 修掉两个真 bug
**① 前景方向判断错误**
原写法"前景像素 >50% 就反相"，会把「锁」「主页」这类**实心图标整个反相**。
改成看**外圈一圈像素**的明暗来判断背景 —— 图标四周总有留白，这个判据稳。

**② 裁剪拉伸破坏宽高比（更严重）**
原写法裁到外框后直接拉伸到 64×64。实测「减号」这种细长条被拉成
**100% 前景的实心方块**，跟真正的方块完全无法区分。
改成**居中补成正方形再缩放**，宽高比得以保留（减号前景占比回到 15.6%）。

两项修复后：**模板自检 top1 正确 25/25**（原 19/25）。

### 新增 fitEllipse（geo_analyze.py）
外接框拿不到倾角，fitEllipse 能。实测精度：

| 真值 | 实测 | 误差 |
|---|---|---|
| 中心 | — | **0.10 px** |
| 倾角 30° | 30.1° | **0.1°** |
| 倾角 75° | 74.7° | 0.3° |
| 长短轴 120/60 | 120/60 | **零误差** |

OpenCV 的 fitEllipse 有两个坑，代码里已归一：
- 返回角度范围 [0,180)，且长短轴可能互换 → 统一成长轴 ≥ 短轴、角度补 90°
- 可能比真值差 90° → 取模到 [0,180)

### 关于 matchShapes（Hu 矩）：评估后未采用
实测它比 IoU 更能抗旋转（自检 21/25 vs 19/25），但有个致命缺陷：

```
圆环加号 vs 圆环减号  → Hu 距离 0.0000（完全无法区分）
圆环加号 vs 圆环关闭  → Hu 距离 0.0000
                        IoU 差异 0.174 / 0.420（能区分）
```

**Hu 矩只看最外层轮廓**，圆环内部的十字/横杠全被丢弃。
所以最终选了「旋转不变 IoU」——在 0/±15/±30/±45 度里取最好角度，
既保留内部细节，又比固定角度 IoU 抗旋转。
`match_detail()` 会同时给出 IoU 和 Hu，便于排查。

旋转不变性实测：真实图标开/关旋转结果一致（0° 优先命中），
人为旋转 15° 时能给出候选但分数偏低 —— **UI 图标几乎不会旋转，
这个能力属于锦上添花，不是关键**。

## 三个坑

**① `PYTHONPATH` 顺序**
`rapidocr` 在持久盘 pylibs，但那里的 numpy 是坏的（缺 `_expired_attrs_2_0`）。
必须**系统路径在前**：`sys.path.append(pylibs)`，不能用 `insert(0, ...)`。
`ui_scan.py` 里已处理。

**② 归一化必须裁外框**
模板匹配前要先裁到前景外接框再缩放到 64×64。直接缩放会因大片空白导致形状错位，IoU 全部崩到 0.2 左右。
`icon_match.py` 的 `_norm_mask()` 里已处理 —— 且是**补成正方形**再缩放，不是直接拉伸（见更新记录）。

**③ 旋转时不要二次裁剪**
`_rot_mask()` 只旋转、不裁外框、不改尺寸。早期版本转完又裁又拉伸，
尺度会漂，导致"转过去再转回来"无法复原，旋转补偿失效。
